### 1.1 Per-request-table column detail (from `database.types.tmp.ts`)

All eight `*_requests` tables share the same skeleton:
- `id uuid PK`
- `user_id uuid NOT NULL` (logical FK to `users.id` / `auth.users.id`)
- `service_id text NOT NULL` (looks like a denormalized service tag)
- `status text NOT NULL` (default `draft`/`pending` per migrations)
- `request_code text NULL` (human code generated by `generate_<svc>_request_code`)
- `submitted_at timestamptz NULL`
- `case_study_date timestamptz NULL` (added 202605030001 across all 8)
- `additional_info text NULL`
- `created_at`, `updated_at timestamptz`
- One column per uploaded document, each `text NULL` and FK to `request_attachments.uid`

Service-specific document slots (each is `text NULL` referencing `request_attachments(uid)`):

### 1.2 `request_attachments` (the unified attachment table, created in `202604040001_request_attachments.sql`)

```
uid                 uuid PK default gen_random_uuid()
request_uid         uuid NOT NULL          -- logical FK to *_requests.id
request_table       text NOT NULL          -- discriminator, CHECK list of 8 tables
file_type           text NOT NULL          -- e.g. abstract, bill, voterId, ...
path                text NOT NULL          -- storage path in 'request-documents' bucket
status              text NOT NULL default 'pending' -- pending|approved|action_required|in_progress|resubmitted (per 202604070002 + 202604070011)
reason_for_action   text NULL
additional_reason   text NULL
created             timestamptz default now()
updated             timestamptz default now()
```

Indexes:
- UNIQUE `(request_table, request_uid, file_type)`
- `(request_table, request_uid)`
- `(status)`
- `(path)`

Triggers:
- `request_attachments_updated` (BEFORE UPDATE) - bumps `updated`
- `trg_cleanup_request_attachments` (AFTER UPDATE/DELETE) - calls `private.dispatch_request_attachment_cleanup` -> POSTs to `storage-cleanup` edge function via `pg_net`

RLS:
- ENABLED
- Policy `Users can manage their own request attachments` - `USING / WITH CHECK public.can_access_request_attachment(request_table, request_uid)`

### 1.3 `audit_logs` (created `202604070003`, finalised `202604070010`)

```
id                  uuid PK
request_id          uuid NOT NULL          -- direct FK-equivalent (enforced by trigger), points to whatever *_requests row
request_table       text NOT NULL          -- CHECK against private.audit_service_tables
action              text NOT NULL          -- CHECK in ('INSERT','UPDATE','DELETE')
old_status          text NULL
new_status          text NULL
changed_by          uuid NULL              -- FK auth.users(id) ON DELETE SET NULL
changed_by_role     text NULL              -- 'user' | 'admin:<service_type>' style
changed_at          timestamptz default now()
```

Constraint `audit_logs_event_shape_chk` enforces:
- INSERT -> `new_status` not null
- UPDATE -> `old_status <> new_status`
- DELETE -> `new_status = 'deleted'`

RLS enabled (`202604070012`):
- SELECT policy: `public.can_read_audit_log(request_table, request_id)` - requester or matching service-admin (currently only `is_medical_admin` for medical/treatment/hospitalization)
- ALL policy `false/false` to block client writes (logging is trigger-only)

## 7. Duplication / denormalization smells

### 7.1 Eight near-identical `*_requests` tables (HIGH severity)

`burial_requests`, `columbarium_requests`, `cremation_requests`, `financial_requests`, `hospitalization_requests`, `medical_requests`, `monetary_requests`, `treatment_requests` share ~10 identical columns (`id`, `user_id`, `service_id`, `status`, `request_code`, `submitted_at`, `case_study_date`, `additional_info`, `created_at`, `updated_at`) and differ only in which document slots they expose. Strong candidate to unify into a single `requests` table with `service_type text/enum` plus the existing `request_attachments` for documents (which already encodes `file_type` per row).

Evidence: `database.types.tmp.ts` lines ~95-1100; CHECK list in `request_attachments` migration (`202604040001`).

### 7.2 Document-slot columns duplicate `request_attachments` (HIGH)

Every `*_file` column on the request tables is a `text` FK to `request_attachments.uid`, and `request_attachments` already has UNIQUE `(request_table, request_uid, file_type)`. So the same logical link is stored in two places: as a column in the request row AND as a row in `request_attachments`. This requires the resync migration `202604040003_sync_request_file_columns_to_attachment_uid.sql` and is exactly the kind of denormalization that drifts. Recommend: keep `request_attachments` as the source of truth and drop the per-slot columns (or convert them into views).

### 7.3 Status, role, service_type, file_type stored as `text` (HIGH)

No Postgres enums anywhere (`Enums: { [_ in never]: never }`). Instead:
- `*_requests.status`, `request_attachments.status`, `audit_logs.action`, `audit_logs.old_status`/`new_status` - all text with CHECK constraints scattered across migrations (`pending`, `approved`, `action_required`, `in_progress`, `resubmitted`, `draft`, `deleted`, ...).
- `admins.service_type`, `admins.role`, `admin_notification.request_table`, `audit_logs.request_table`, `request_attachments.request_table` - all text discriminators repeating the same 8-value vocabulary as the table list.
- `request_attachments.file_type` - free-form text (`abstract`, `bill`, `voterId`, `medCert`, `rx`, ...). Should be an enum or a small lookup table.
- `financial_requests.financial_request_type`, `burial_requests.coverage`, `cremation_requests.coverage` - text, no constraint visible.

Recommend converting these to `CREATE TYPE ... AS ENUM` (or lookup tables if values change at runtime). Status helper RPCs (`is_action_required_request_status` etc.) already act like an enum-validation layer - making it formal would let those collapse.

### 7.4 `admin_notification.request_id` and `.request_table` duplicate `audit_logs` (MEDIUM)

`admin_notification` already FKs `audit_log_id`, and `audit_logs` already stores `request_id` + `request_table`. Storing them again on `admin_notification` is denormalization (the same is true to a lesser degree on `user_notification`, which avoided this by joining only on `audit_log_id`). The `user_notification` design is the right pattern; `admin_notification` should follow it.

### 7.5 `monetary_requests` column naming drift (LOW)

While other tables use clear separate slots (`valid_id_file`, `voter_id_file`, `birth_cert_file`), `monetary_requests` collapses them into composite-name columns: `valid_id_or_birth_cert_file`, `voters_id_or_cert_file`, `additional_attachment_file`. This is a leaky-encoded enum in column names; once requests are unified per 7.1, this evaporates.

### 7.6 Personal info on `users` likely duplicated in `auth.users` raw_user_meta (LOW, can't confirm without dump)

`users.email` mirrors `auth.users.email`; `first_name`/`last_name`/`birth_date` are commonly also written into `auth.users.raw_user_meta_data` by Supabase Auth. Worth verifying with a dump and keeping `public.users` as the source of truth.

### 7.7 Multiple historical audit-log table designs in migration history (informational)

Migrations show four iterations: `audit_logs` (single) -> `audit_logs_v2` + per-service `audit_logs_<svc>` (`202604070007`) -> flattened `audit_logs_single` (`202604070008`) -> back to a single `audit_logs` with status-change semantics (`202604070009`/`10`). End state is one table. Verify on remote via dump that none of the abandoned tables (`audit_logs_v2`, `audit_logs_hospitalization`, ..., `audit_logs_single`, `audit_request_refs`, `audit_service_tables`) survived as zombies in `public`. (`audit_service_tables` was intentionally moved to `private`.)

### 7.8 `request_attachments.path` and `*_requests.<file>_file` (MEDIUM)

If any code path still writes legacy storage paths into request-row columns instead of (or in addition to) `request_attachments.path`, you have two sources of truth for the storage URL. The 202604040003 migration syncs them once - ongoing writes need to be audited in app code.
