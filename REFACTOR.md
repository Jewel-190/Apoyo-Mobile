# Apoyo modular refactor — running log

This document is the **single source of truth** for the modular refactor that
was started in May 2026. It explains:

1. The architectural intent.
2. What changed in mobile, in the backend, and in the admin app.
3. How the new pieces are meant to be consumed by future code (especially
   the planned superadmin "manipulate any request" feature).
4. How to add a new service to the system end-to-end.
5. Rollback notes per phase.

If you are picking this work up later, **read this whole file first**.

---

## 0. Why we did this

Before the refactor:

- **Mobile** had eight near-identical `*Req.tsx` screens, each ~1,600 LOC,
  each duplicating the same draft → upload → submit lifecycle, the same
  swipe-to-delete row, the same NetInfo banner, the same status maps, etc.
  Service-id ↔ Postgres-table ↔ route-path mappings were copy-pasted in 5+
  files and had drifted (`columbarium` vs `colombarium`).
- **Backend** had eight near-identical `*_requests` tables and per-row
  `*_file` columns that duplicated rows already living in
  `request_attachments`. Migration `202604040003_sync_request_file_columns_to_attachment_uid.sql`
  exists *because of* that drift.
- **No generated DB types** anywhere. The Supabase client was untyped on
  both apps.
- The planned **superadmin "manipulate any request"** feature would have
  needed to either (a) duplicate per-table CRUD for all eight tables or
  (b) bypass the normal app data layer entirely.

The refactor does **not** physically unify the eight `*_requests` tables.
It puts a **safe facade** on top of them so application code can read and
write requests through one contract while the storage stays partitioned.
This was a deliberate trade-off: less reward than full unification, but
zero risk to the live admin pipeline that hardcodes the eight table names.

```
        ▼                                                     ▼
   shared/data (mobile)                            src/shared/data (admin)
   ─ supabase.ts (typed client)                    ─ supabaseClient.js
   ─ requests.ts (createDraft / submit / list)     ─ requestData.js

   ─ notifications.ts                                (wraps admin_request_op RPC)
        │                                                     │
        ▼                                                     ▼
   ┌───────────────────────────────────────────────────────────┐
   │                   Supabase backend                        │
   │                                                           │
   │   8 *_requests tables (kept; primary write target)        │
   │   request_attachments (single source of truth for files)  │
   │   audit_logs                                              │
   │                                                           │
   │   NEW: requests_v          UNION view, single read shape  │
   │   NEW: admin_request_op    SECURITY DEFINER write RPC     │
```

The same `shared/domain/` files live verbatim in both apps. A small
PowerShell script (`scripts/sync-shared.ps1`) regenerates
`database.types.ts` and copies the canonical `shared/domain/` from this
mobile repo into `ApoyoAdmin/src/shared/domain/`.

```
    supabase.ts                         ← typed Supabase client
    requests.ts                         ← typed CRUD (createDraft/submit/list/get)
    attachments.ts                      ← list/upsert/delete request_attachments
    notifications.ts                    ← typed notifications edge fn wrapper
    storage.ts                          ← upload helpers for request-documents
    index.ts
  hooks/
    useRequestForm.ts                   ← draft + upload + submit lifecycle hook
    useAuthSession.ts                   ← session + cached profile
    index.ts
  components/

                                          re-exports from shared/* so old

```

**Important:** `lib/*.ts` files are **not deleted**. They re-export from
their `shared/` equivalents. Existing screens continue to import from
`lib/...` and there is no behavioural change. New code should import from
`shared/`.

The eight `*Req.tsx` and the eight `SubmissionSuccess.tsx` screens are
**not all migrated in this pass**. `FinancialReq.tsx` is migrated as the
reference implementation; the other seven keep their working inline
implementations until they are migrated one-by-one in follow-up commits
using the same pattern. See [§7](#7-how-to-migrate-a-req-screen).

## 3. New admin layout

The admin repo (`ApoyoAdmin`) gets a parallel `src/shared/` with the same
`domain/` folder. It also gets:

- `src/shared/data/requests.js` — small wrapper over `requestData.js` so
  cross-cutting code can talk to one API while the existing
  per-role-table flow keeps working.
- `src/shared/data/adminRequestOps.js` — client for the new
  `admin_request_op` RPC; intended for the future superadmin module.
- `src/superadmin/modules/RequestsManagement/` — skeleton module that
  demonstrates the future "manipulate any request" pattern. It mirrors
  the UI feel of `ContentManagement/` but uses real Supabase reads
  (`requests_v` view) and real writes (`admin_request_op` RPC).

**Critical:** `roleConfig.js`, `requestData.js`, `requestDbStatus.js`, and
all admin pipeline screens (`Applications/*`, `ForApproval/*`) are **not
rewritten**. They are the working production pipeline and the refactor
explicitly stays out of their way.

## 4. New backend pieces

### 4.1 `shared/types/database.types.ts`

Generated by:

```sh
npm run supabase -- gen types typescript --linked > shared/types/database.types.ts
```

The PowerShell script `scripts/sync-shared.ps1` runs this and then strips
any CLI prelude noise that Windows sometimes prepends.

### 4.2 Migration `202605090001_safe_facade.sql`

**Purely additive.** Adds:

- Postgres enums:
  - `public.request_status` — every status string already in use across
    `*_requests` tables and `audit_logs.new_status`.
  - `public.service_type_id` — the eight service-line discriminators.
  - `public.attachment_file_type` — UI-side file_type slot keys.
  - `public.attachment_status` — values used in `request_attachments.status`.
- View `public.requests_v` — UNION ALL across the eight `*_requests`
  tables, projecting the shared columns plus a `service_type` discriminator
  and the source `request_table` text. SECURITY INVOKER (default) so RLS
  on the underlying tables is preserved.
- Helper `public.is_superadmin(uid uuid) returns boolean` — reads
  `admins.role`.
- RPC `public.admin_request_op(op, service_type, request_id, patch)` —
  SECURITY DEFINER, gated by `is_superadmin(auth.uid())`, dispatches
  `insert` / `update` / `delete` / `transition_status` to the correct
  `*_requests` table and writes a corresponding row to `audit_logs`.

**Does not** rewrite any existing column, drop anything, or change RLS on
existing tables. Safe to apply to the live project at any time. To apply
once you have the DB password / Docker:

```sh
npm run supabase -- db push
```

If you don't want to push it from this repo because of the migration
drift documented in `supabase/README.md`, you can copy the migration body
into the Supabase SQL editor and run it manually.

### 4.3 Migration `202605090002_drop_redundant_file_columns.sql` (DRAFT — Phase 10)

**Destructive.** Drops every per-service `*_file` column. **Not applied
automatically.** This file is staged in `supabase/migrations/_phase10/`
(outside the regular migrations folder) and must be moved into
`supabase/migrations/` and applied manually only after a full smoke pass
confirms no application code reads these columns. See [§9](#9-phase-10-when-and-how).

## 5. Status enum reference

The DB-canonical lowercase strings are:

| DB literal              | UI label          | Used by                                             |
| ----------------------- | ----------------- | --------------------------------------------------- |
| `draft`                 | Draft             | mobile while user fills form, hidden from admin     |
| `pending`               | Pending           | newly submitted requests                            |
| `in progress`           | In Progress       | admin opened the request                            |
| `action required`       | Action Required   | admin sent specific attachments back                |
| `resubmitted`           | Resubmitted       | applicant uploaded fixed attachment                 |
| `for approval`          | For Approval      | review complete, awaiting scheduling                |
| `scheduled`             | Scheduled         | case study interview is scheduled                   |
| `case study`            | Case Study        | post-interview, awaiting final approval             |
| `approved`              | Approved          | terminal: assistance granted                        |

Lowercase phrases (`in progress`, `action required`, `for approval`,
`case study`) match the DB CHECK constraints — do not change to
underscores. The Postgres enum `request_status` introduced in Phase 2
contains exactly this list (the value `case study` is included even though
it appears only in `audit_logs.new_status` so the enum can be reused
there in the future).

## 6. Service registry

`shared/domain/services.ts` is the **one** place to look up everything
about a service. It exposes:

```ts
export const SERVICES: Record<ServiceId, ServiceDefinition>;
export const SERVICE_LIST: ServiceDefinition[];

export function getService(id: string | null | undefined): ServiceDefinition | null;
export function getServiceByTable(table: RequestTableName): ServiceDefinition | null;
export function tableForService(id: ServiceId): RequestTableName;
export function reqRouteForService(id: ServiceId): string;
```

The shape of `ServiceDefinition` includes `id`, `label`, `category`,
`requestTable`, `requestRoute`, and the per-service file slot list. See
[shared/domain/services.ts](shared/domain/services.ts) for full details.

The registry deliberately accepts **both** `columbarium` and the
historical typo `colombarium` and normalizes them in
`getService()`. The DB still uses the legacy `colombarium` UI slug in
some places (e.g. `lib/serviceRequirements.ts`); both forms map to the
canonical `columbarium_requests` table.

## 7. How to migrate a Req screen

The reference migration is `app/Home/Financial/FinancialReq.tsx`.
Pattern:

1. Look up the service in `shared/domain/services.ts` and confirm the
   `fileSlots` list matches the form fields.
2. Replace the inline `getUser`, draft-creation, attachment-upsert, and
   submit logic with `useRequestForm({ serviceId })`.
3. Wrap the JSX in `<RequestFormShell>` and render one
   `<AttachmentSlot>` per `fileSlot`.
4. Move any per-service custom JSX (e.g. the `financial_request_type`
   picker on `FinancialReq.tsx`) into the `extras` slot of the shell.
5. Verify the screen still loads, drafts save, files upload, and submit
   transitions to `pending`.

The shell + hook deliberately preserve the existing UX 1:1 — same
swipe-to-delete, same NetInfo banner, same Android back-press modal,
same error toasts. The only thing that changes is where the code lives.

## 8. How to add a new service end-to-end

This is the payoff of the refactor. A new service used to require
edits across 8+ files and the DB.

1. **DB:** add `<service>_requests` table (mirror an existing one), add
   it to the union in the `requests_v` view (a follow-up migration), and
   add the service-id to the `service_type_id` enum.
2. **Mobile:**
   - Add the entry to `shared/domain/services.ts` (id, label, category,
     route, table, fileSlots).
   - Add the route folder under `app/Home/<NewService>/` with a thin
     `*Req.tsx` that calls `useRequestForm({ serviceId: 'newservice' })`
     and a tiny `SubmissionSuccess.tsx`.
   - Add the entry to `lib/serviceRequirements.ts` (which holds the
     rich content/tips — kept where it is for now).
3. **Admin:** add the table name to the appropriate role's
   `requestSources` in `src/shared/config/roleConfig.js` and add the
   field labels in `FIELD_LABELS_BY_SOURCE_TABLE`. Existing pipeline
   screens pick it up automatically.
4. **Backend analytics:** add the table to `TABLES_BY_ROLE` in the
   `admin-dashboard-analytics` edge function (cross-repo contract).

## 9. Phase 10: when and how

`supabase/migrations/_phase10/202605090002_drop_redundant_file_columns.sql`
is the **destructive** migration that finally removes the per-service
`*_file` columns. Pre-flight checklist before promoting it from
`_phase10/` to `migrations/`:

- [ ] `rg "letter_file|voter_id_file|valid_id_file|...etc" --type=ts --type=tsx --type=jsx --type=js` returns **zero** results in both repos for `Update`/`Insert` shapes.
- [ ] `request_attachments` row count for the relevant `(request_table, request_uid)` pairs equals or exceeds the count of non-null `*_file` columns on the corresponding rows.
- [ ] At least 7 days have passed since the new code shipped to all clients and you have no reports of upload failures.
- [ ] Backup the DB.

Then move the file into `supabase/migrations/` (rename if needed so the
timestamp is current) and apply.

If the smoke pass turns up *any* read of those columns, fix the read
first, ship a new client, wait, and re-evaluate.
